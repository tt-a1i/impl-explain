## A. round-2 三处 P0 的真实成色

### A1. 路径查找 fallback — **延后一步，没解决**

`render.py` 实际只在 `/Users/admin/code/impl-explain/scripts/render.py`。逐条核对：

- 4 条 explicit path（`~/.agents`、`~/.claude/skills`、`~/.codex/.agents`、`~/.config/opencode/skills`）实测全 miss。
- 限定 find（`find ~/.claude ~/.codex ~/.config ~/.agents -maxdepth 6 -path '*impl-explain*' -name 'render.py'`）我**真实跑了一次**：exit 0，stdout 空。

也就是说，round-3 给的"受限 find 兜底"在 dev-clone 场景下**纯粹是延后一步告诉用户"未安装"**，没解决问题。任何把 skill 放在 `~/code/`、`~/dev/`、`~/work/` 等开发目录的人都会被卡住。正确的 fallback 应该是：(a) 用 framework 暴露的 SKILL.md 绝对路径反推 `<SKILL.md dirname>/scripts/render.py`；或 (b) 加 `IMPL_EXPLAIN_HOME` 环境变量；或 (c) 让 install.sh 写一个 `~/.impl-explain-path` 记录。继续往 `~/.claude ~/.codex` 里翻 maxdepth 6 是治标——目录树扩大几条还在那几个 home 子目录里，dev clone 永远 miss。BSD `find -maxdepth` 语法已实测，macOS/Linux 都用 `-maxdepth N`，这点不是问题。

### A2. 关键词重合度算法 — **从"问得太多"退化成"沉默选错"**，比 round-2 更危险

我在 global-hotspot-globe（184 plans, 当前分支 vs origin/main 共 255 commits）按 SKILL.md 步骤 1 的算法**实跑了一次**，停用词 = `{the, a, and, 的, 了, 和}` + len ≤ 2 过滤：

| rank | overlap | plan |
|---:|---:|---|
| 1 | 28 | 2026-04-27-agent-only-schema-cleanup.md |
| 2 | 22 | 2026-04-25-content-pipeline-precision-gap-l4.md |
| 3 | 21 | 2026-04-26-content-related-insights.md |
| … | | |
| **38** | **14** | **2026-05-11-unified-source-sync-manager.md** ← 用户真正想要的 |
| 78 | 12 | 2026-05-11-gdelt-gkg-ingester.md |

top1 - top2 = **6**，远超阈值 2 → 算法**不会问用户**，会自信地选错 plan。root cause 是 plan 模板首屏 boilerplate（`superpowers / tracking / required / implementation / task / this / plan / plans / sub / driven / recommended`）对每条 plan 贡献都很大，覆盖了真正区分性的领域 token。round-2 算法说"差距 < 2 就问"——本意是"撞了就保守"，round-3 把规则照搬实跑后反而被 boilerplate 偏置，更糟。

题主问的"两个 sync plan 会不会都命中 5-6 个导致差距 < 2"实测**没发生**，反而出现了完全无关的 plan 把日期最新的真 plan 挤到 38 名。**hyphenated 切分加重了这个偏置**：`source-sync` → `{source, sync}` 都是高频通用词，`gdelt-gkg` → `{gdelt, gkg}` 极稀有但只命中两次。算法不带 IDF/权重，奖励"通用 token 出现多次"的 plan。

补救方向：(a) 先剥掉 plan 模板首屏 boilerplate（截掉 `>` quote 区 + `**For agentic workers**` 段）再取 token；(b) 只对 `## Goal` / `## Approach` / `## Files` 段取 token；(c) 加 IDF——对 plans 目录全量算 token DF，只保留 DF ≤ N/3 的 token。任选其一，建议 (a)+(b) 组合，最便宜也最确定。

### A3. mitigation 同义词 — **覆盖确有提升，仍漏一个高频中文表达**

round-3 列了 partial 触发词：`future / 后续 / 上线后 / 上线后再调 / TODO / 暂未 / 未接入 / 已沉淀 / 已记录 / 部分覆盖 / long-term / 需补`。覆盖明显增厚。

但我拿 round-2 报告里实测踩坑的那句 — **"短期缓存，长期需补 backfill 路径"** — 走一遍：`需补`命中，OK。换一种常见写法："长期看需要补 backfill" → `需补`不连续，靠的是`长期`+`需要`各自识别。round-3 列表里有 `long-term` 但**没有中文 `长期`**。Plan 里中文叙述用"长期"很多（短/中/长期是常见词组），漏了它会让 partial 误判成 none。建议补三个词：`长期`、`需要 + 任意动词`正则、`后期`。其他同义词已经够。

## B. round-3 新引入的问题

- **停用词太短 + token 切分粗糙**：6 词中英文停用词无法覆盖 plan 模板里的 `this/plan/plans/task/superpowers/tracking/required/implementation/sub/driven/recommended`——A2 实测的 38 名问题根因。建议要么扩到 30+ 词，要么换 IDF 路线。hyphenated word 现切成多个普通 token（`source-sync` → 两个高频词），让稀有词反而吃亏。
- **question 字段的诱导**：schema 仍然接受 question，SKILL.md 也写"可选"，但 plan 详细时 agent 倾向"既然字段在就填上"。**实测建议**：把 question 从 schema 里完全移除（render.py L1160 已经不显示了），让"不渲染的字段"在 schema 上也消失，避免误导。
- **BSD/GNU `find -maxdepth`**：macOS BSD find 和 Linux GNU find 都用 `-maxdepth N`，已实测 OK，非问题。
