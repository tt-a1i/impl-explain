把 RSS、Pulse/API、GDELT GKG、agent source fetcher 四类数据源统一收敛到一个注册表 + 一个后台调度器里管。
怎么做

Decisions

6 decisions · 5 chosen · 1 deferred
01

集中注册表放 cadence

采用 单一 SourceSyncDefinition 注册表，新增 source 只改一处

47+ 数据源后 "新增一个去哪里加" 是 grep 八处的痛点。注册表 = 所有 source 强制 declare 一致字段（kind / cadence / pulse_definition）。

放弃每个 runner 内部各自声明 cadence · config.py 里 47 个独立常量

代价多一层抽象；新增 source kind 时需要在 SourceSyncService._run_definition 加分支。

02

灰度时禁用 legacy loop

采用 SOURCE_SYNC_ENABLED=true 时抑制旧 RSS/GDELT/pipeline loop，重启切换

并存 = 双写 DB 造成 published article 重复（projection / snapshot 表都会污染）；直接删除没法 fallback；开关切换 + 重启是工程上最稳的灰度路径。

放弃新旧并存（让旧 loop 也跑） · 直接删除旧 loop

代价SOURCE_SYNC_ENABLED=false 时还在跑 legacy；切换必须重启服务。

03

Profile 字符串映射 include set

采用 字符串 profile（content / pulse / rss-only / gdelt 等）→ include set

部署场景固定的几种组合（pulse-only debug、rss-only 灰度、full prod），profile 一行配置即可。完整 list 配置噪声大且易写错。

放弃让用户传完整 include list · 硬编码全部跑

代价加新 profile 要改 source_sync_profile_include 代码；profile 写错时静默落到 default。

04

单全局 semaphore 控并发

采用 asyncio.Semaphore，cap = source_sync_max_concurrency（默认 4）

47 pulse 同时打会触上游 rate limit；多 semaphore 工程复杂度上升收益不明显；先用单 semaphore 看效果。

放弃每个 kind 独立 semaphore · 完全不限制并发

代价慢 source 会占着信号量阻塞快的；future 可改 per-kind 队列。

05

60s tick + cadence 检查

采用 Scheduler 60 秒 tick，每 tick 算哪些 definition due

cadence 多样（15min ~ 24h），tick 实现极简；60s 精度对所有现有 cadence 足够；事件驱动需要额外队列基础设施。

放弃事件驱动（来一个 trigger 跑一个） · 全部固定 cron 表达式

代价单次 tick 内最大 60s cadence drift（业务可接受）。

06

失败本轮跳过, 下轮再来

推迟 捕获并 log.warning，本轮记 status=failed，下一轮 tick 再来

实施期暂未观测到 transient 失败热点；多数 source 自身有 cache 机制；retry 需要复杂的失败计数和 backoff 状态机。

放弃立即 retry with backoff · 失败后 disable definition

代价短暂故障期会持续 log.warning 噪声；future 可加 circuit breaker。

Out of Scope

  • 失败重试策略（无 backoff，下一 tick 再来）
